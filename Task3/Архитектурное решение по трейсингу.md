# Архитектурное решение по трейсингу

## 1. Анализ системы и точки потенциальных сбоев

На основе текущей архитектуры (Online Store → RabbitMQ → MES → RabbitMQ → CRM, а также B2B API → MES) выявлены следующие критические границы, где заказ может «сломаться», потеряться или зависнуть. Именно эти места должны быть покрыты трейсингом в первую очередь:

1. **Online Store → RabbitMQ**: Момент отправки сообщения о создании заказа (`SUBMITTED`). Сбой: сообщение не создано или не доставлено в брокер.
2. **RabbitMQ → MES (Consumer)**: Момент получения сообщения MES для расчета стоимости. Сбой: сообщение потеряно, нет ACK, или воркер MES упал/завис.
3. **Внутри MES**: Процесс расчета стоимости 3D-модели. Сбой: долгая обработка (до 30 минут) без обновления статуса, блокировка потока или падение приложения.
4. **MES → RabbitMQ → CRM**: Отправка статуса `PRICE_CALCULATED` или `MANUFACTURING_STARTED`. Сбой: CRM не получает обновление, и заказ визуально «зависает» для менеджеров.
5. **B2B API → MES**: Внешний вызов. Сбой: внешний партнер не получает ответ, а сообщение внутри нашей системы теряется.

## 2. Список данных для трейсинга

Для эффективного расследования инцидентов каждый трейс (Trace) и спан (Span) должен содержать:
* **Идентификаторы**: `TraceID` (сквозной, генерируется при создании заказа), `SpanID` (уникален для каждой операции), `ParentSpanID`.
* **Бизнес-контекст**: `OrderID` (обязательно для корреляции с бизнес-логикой), `UserID` (хэшированный или анонимизированный), `OrderSource` (`b2c` или `b2b`).
* **Временные метки**: Время начала (`start_time`), время окончания (`end_time`), длительность (`duration_ms`).
* **Результат операции**: Статус (OK, ERROR), HTTP-статус код или код ошибки AMQP, тип исключения (если есть).
* **Метаданные сервиса**: Имя сервиса (`online-store`, `mes-backend`, `crm-backend`), версия приложения, имя хоста/пода.
* **События (Logs/Events)**: Ключевые переходы статусов заказа (например, "Переход в статус PRICE_CALCULATED").

## 3. Мотивация

Внедрение распределенного трейсинга необходимо для перехода от «гадания на кофейной гуще» при поиске потерянных заказов к точному, основанному на данных, расследованию инцидентов.

**Что это даст компании:**
* **Сокращение времени на расследование (MTTR)**: Вместо ручного поиска по логам трех разных систем, инженер видит весь путь заказа на одной временной шкале за секунды.
* **Доказательная база для споров с B2B-партнерами**: Мы сможем точно сказать, дошло ли сообщение от партнера до нашего API и на каком этапе оно было обработано.
* **Выявление скрытых узких мест**: Наглядная визуализация покажет, какие именно этапы (например, конкретный запрос к БД внутри MES) вносят основной вклад в 30-минутную задержку.

**Метрики, на которые повлияет внедрение:**
1. *Бизнес-метрика*: Количество жалоб на «потерянные» заказы (цель: снижение на 80% за квартал).
2. *Бизнес-метрика*: Среднее время выполнения заказа от `SUBMITTED` до `PRICE_CALCULATED` (SLA adherence).
3. *Техническая метрика*: MTTR (Mean Time To Recovery) для инцидентов категории "Integration Failure" (цель: снижение с часов до минут).
4. *Техническая метрика*: Процент заказов, по которым доступен полный сквозной трейс (цель: > 99%).

## 4. Предлагаемое решение

Для реализации сквозного трейсинга предлагается использовать стандарт **OpenTelemetry (OTel)** как наиболее универсальное и/vendor-neutral решение.

**Технологический стек:**
1. **OpenTelemetry SDK**: Внедряется в код приложений (Java для Online Store и CRM, C# для MES).
2. **OpenTelemetry Collector**: Отдельный сервис, который принимает трейсы от приложений, обогащает их (например, добавляет теги окружения) и экспортирует в хранилище. Это снимает нагрузку с приложений и позволяет гибко менять бэкенд.
3. **Хранилище и визуализация**: **Jaeger** (или Grafana Tempo, если уже используется Grafana из Задания 2). Рекомендуется Jaeger из-за отличной поддержки и простоты развертывания.

**Необходимые доработки:**
* Настроить автоматическую генерацию и передачу `TraceID` и `SpanID` через заголовки HTTP и свойства сообщений RabbitMQ (message properties).
* Добавить инструментацию для RabbitMQ (Spring AMQP для Java, RabbitMQ.Client для C#), чтобы создание и потребление сообщений формировали отдельные спаны.
* Развернуть инфраструктурные компоненты (Collector, Jaeger) в облаке (например, как дополнительные сервисы в Kubernetes или на выделенных EC2).




## 5. Компромиссы

1. **Накладные расходы на производительность**: Сбор и отправка трейсов потребляет CPU и сеть (обычно 1-5%). Для высоконагруженных успешных сценариев необходимо настроить **сэмплирование** (например, сохранять 10% успешных трейсов, но 100% трейсов с ошибками или длительностью > 5 секунд).
2. **Стоимость хранения**: Трейсы занимают много места. Необходима политика удержания (retention policy), например, хранение детальных трейсов только 7 дней, после чего они удаляются или агрегируются.
3. **Ограничения внешних систем**: Мы не можем заставить B2B-партнеров внедрять OpenTelemetry. Трейсинг будет начинаться только с момента входа запроса в наш API Gateway / Online Store.
4. **Сложность инструментации легаси**: Если в MES есть унаследованные фоновые задачи, не поддерживающие асинхронную передачу контекста, их покрытие трейсингом потребует значительного рефакторинга кода.

## 6. Безопасность

1. **Маскирование чувствительных данных (Data Masking)**: Категорически запрещено передавать в трейсы PII (персональные данные: имена, телефоны, email) и содержимое 3D-файлов. В спаны должны попадать только обезличенные идентификаторы (`OrderID`, анонимизированный `UserID`). На уровне OpenTelemetry Collector необходимо настроить процессоры для фильтрации/хэширования таких полей.
2. **Контроль доступа (RBAC)**: Доступ к интерфейсу Jaeger должен быть ограничен корпоративной сетью (VPC) и требовать аутентификации. Просмотр трейсов разрешен только ролям: "Разработчик", "DevOps", "Техническая поддержка" (через интеграцию с корпоративным SSO, например, Keycloak или Yandex ID).
3. **Защита каналов связи**: Передача данных от приложений к OpenTelemetry Collector должна происходить по защищенным внутренним каналам (внутри VPC), без вывода портов Collector в публичный интернет.


## 7. Дополнительное задание: Автоматический мониторинг и алертинг на основе трейсинга

Трейсинг не должен быть только инструментом для ручного расследования. Мы можем использовать данные трейсов для проактивного алертинга о "зависших" заказах.

**Решение:**
1. **Генерация метрик из трейсов**: OpenTelemetry Collector настраивается так, чтобы на основе входящих спанов генерировать агрегированные метрики (например, количество спанов с определенным `OrderID` и статусом, или гистограмму длительности переходов между статусами) и отправлять их в **Prometheus** (из Задания 2).
2. **Правило алертинга (Alerting Rule)**: В Prometheus создается правило, которое отслеживает метрику `order_status_transition_duration_seconds`. 
   * *Логика*: "Если для `OrderSource=b2b` или `b2c` существует спан со статусом `SUBMITTED`, но в течение 10 минут не появилось ни одного последующего спана с `PRICE_CALCULATED` или `ERROR` для этого же `TraceID`/`OrderID`".
3. **Действие**: Alertmanager отправляет уведомление в канал Slack/Telegram команды разработки и автоматически создает тикет в Jira с прикрепленной ссылкой на соответствующий TraceID в Jaeger.
