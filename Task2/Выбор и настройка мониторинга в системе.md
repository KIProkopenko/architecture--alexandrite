## 1. Мотивация

Внедрение полноценного технического мониторинга критически необходимо для компании «Александрит» по следующим бизнес-причинам:

1. **Остановка потери выручки:** В настоящее время мы теряем крупные B2B-контракты и лояльность B2C-клиентов из-за «пропадающих» заказов. Яндекс Метрика показывает только действия пользователя на фронтенде Internet Shop, но не видит, что происходит с заказом после нажатия кнопки «Сделать заказ». Мониторинг позволит мгновенно обнаруживать, на каком этапе (Shop API → Messages Queue → MES API → CRM API) происходит сбой, и предотвращать потерю данных.

2. **Повышение эффективности операторов:** Жалобы на медленную загрузку дашборда MES напрямую влияют на скорость обработки заказов и, как следствие, на вознаграждение операторов. Мониторинг даст нам объективные данные (а не догадки), чтобы доказать, является ли причиной нагрузка на процессор MES API, нехватка оперативной памяти или блокировки в MES DB. Это обоснует необходимость выделения ресурсов на оптимизацию или масштабирование.

3. **Переход от реактивной к проактивной работе:** Сейчас мы узнаем о проблемах от разгневанных клиентов или партнеров. Система алертинга позволит инженерной команде узнавать о деградации сервиса (например, рост очереди в Messages Queue или увеличение времени отклика MES DB) и устранять проблему до того, как она повлияет на бизнес-процессы.

4. **Обоснование архитектурных изменений:** Чтобы бизнес выделил бюджет на добавление реплик баз данных (Shop DB, MES DB) или новых инстансов API, нам нужны цифры. Мониторинг предоставит неопровержимые доказательства узких мест (например, "CPU MES DB находится на 95% в часы пик").

5. **Контроль SLA для B2B-партнеров:** API user (партнеры) ожидают определенного времени ответа и доступности сервиса. Мониторинг позволит отслеживать соблюдение соглашений и предоставлять партнерам отчеты о качестве сервиса.

## 2. Выбор подхода к мониторингу

Для разных уровней системы мы будем использовать комбинацию двух проверенных подходов, так как они лучше всего закрывают наши текущие боли:

* **Для прикладного уровня (Shop API, CRM API, MES API и интеграция через Messages Queue): подход RED.**
  * **R (Rate):** Количество запросов/сообщений в секунду. Помогает понять реальную нагрузку, особенно с учетом роста на 100 заказов в месяц и нового B2B API.
  * **E (Errors):** Количество ошибок. Критически важно для отслеживания потерянных заказов и сбоев при расчете стоимости.
  * **D (Duration):** Время отклика (латентность). Необходимо для контроля времени расчета 3D-модели и времени загрузки дашборда MES.
  * *Обоснование:* RED идеально подходит для сервисов и бизнес-транзакций, так как напрямую отражает пользовательский опыт и целостность бизнес-процесса (заказа).

* **Для инфраструктурного уровня (EC2 инстансы, Shop DB, MES DB, Messages Queue): подход USE.**
  * **U (Utilization):** Среднее время, в течение которого ресурс был занят (например, загрузка CPU или дисковой подсистемы).
  * **S (Saturation):** Степень очередности запросов к ресурсу (например, длина очереди дисковых операций или нехватка соединений в пуле БД).
  * **E (Errors):** Аппаратные или системные ошибки (например, ошибки ввода-вывода диска).
  * *Обоснование:* Поскольку у нас по одному инстансу на каждое приложение и БД (Shop DB, MES DB), мы должны четко понимать, не уперлись ли мы в физические пределы этих ресурсов, что является наиболее вероятной причиной тормозов дашборда MES.

* **Для фронтендов (Internet Shop, CRM, MES): подход «Четыре золотых сигнала» (Google SRE).**
  * **Latency:** Время загрузки страниц и выполнения действий пользователя.
  * **Traffic:** Количество активных пользователей и их действий.
  * **Errors:** Количество ошибок на клиентской стороне (JavaScript ошибки, неудачные запросы к API).
  * **Saturation:** Загрузка ресурсов браузера (память, CPU).
  * *Обоснование:* Фронтенды напрямую влияют на пользовательский опыт. Операторы MES и продавцы CRM должны иметь быстрый интерфейс для эффективной работы.

## 3. Описание метрик

Ниже приведен список ключевых метрик, выбранных для внедрения. Для каждой указана цель и необходимые ярлыки (labels) для детализации данных.

### Бизнес-метрики и интеграция (Messages Queue - RabbitMQ)
Эти метрики критичны для решения проблемы потерянных заказов.

1. **`orders_created_total`** (Counter)
   * **Зачем нужна:** Базовая метрика для отслеживания общего потока заказов. Позволяет сверять количество созданных заказов в Internet Shop с количеством принятых в CRM API/MES API.
   * **Ярлыки:** `source` (значения: `b2c_web`, `b2b_api`), `status` (INITIATED, SUBMITTED и т.д.).

2. **`rabbitmq_queue_depth`** (Gauge)
   * **Зачем нужна:** Показывает количество сообщений, ожидающих обработки в очереди. Резкий рост этой метрики при стабильном трафике означает, что потребитель (CRM API или MES API) "захлебнулся" или упал.
   * **Ярлыки:** `queue_name` (например, `shop_to_mes_orders`, `mes_to_crm_status_updates`).

3. **`rabbitmq_messages_unacked_total`** (Gauge)
   * **Зачем нужна:** Показывает количество сообщений, которые были взяты в работу, но еще не подтверждены (ACK). Если эта метрика растет, значит, обработка заказа зависла (например, из-за долгого расчета 3D-модели в MES API или дедлока в MES DB), и сообщение не возвращается в очередь.
   * **Ярлыки:** `queue_name`, `consumer_service` (crm-api, mes-api).

4. **`order_processing_duration_seconds`** (Histogram)
   * **Зачем нужна:** Отслеживает время прохождения заказа между ключевыми статусами. Позволит выявить, что расчет стоимости занимает не 2-3 минуты, а 30 минут, и как это коррелирует с размером файла.
   * **Ярлыки:** `transition` (например, `FILE_UPLOADED_to_PRICE_CALCULATED`), `model_complexity_bucket` (оценка количества полигонов: `low`, `medium`, `high`).

### Метрики приложений (Подход RED)

5. **`http_requests_total`** (Counter)
   * **Зачем нужна:** Оценка трафика и частоты ошибок на уровне API. Помогает отделить проблемы сети от проблем приложения.
   * **Ярлыки:** `service` (shop-api, crm-api, mes-api), `method` (GET, POST), `endpoint` (например, `/api/v1/orders`), `status_code` (2xx, 4xx, 5xx).

6. **`http_request_duration_seconds`** (Histogram)
   * **Зачем нужна:** Контроль времени отклика. Критически важна для эндпоинта, отдающего данные для дашборда MES (MES API), и для эндпоинта загрузки 3D-файлов (Shop API).
   * **Ярлыки:** `service`, `endpoint`.

7. **`3d_calculation_duration_seconds`** (Histogram)
   * **Зачем нужна:** Специфичная метрика для MES API, отслеживающая время расчета стоимости 3D-модели. Позволит выявить деградацию производительности вычислительного модуля.
   * **Ярлыки:** `model_complexity_bucket`, `result` (success, error, timeout).

### Метрики баз данных (Подход USE)

8. **`database_cpu_utilization_percent`** (Gauge)
   * **Зачем нужна:** Показывает, насколько загружен процессор управляемой базы данных. Значения выше 80% длительное время сигнализируют о необходимости оптимизации запросов или масштабирования. Критично для MES DB, так как она обслуживает и расчет стоимости, и дашборд операторов.
   * **Ярлыки:** `db_instance` (shop-db, mes-db), `role` (master, replica).

9. **`database_active_connections`** (Gauge)
   * **Зачем нужна:** Показывает количество активных подключений к БД. Рост до максимума пула соединений приведет к тому, что новые запросы (включая загрузку дашборда MES) будут вставать в очередь или получать таймаут. Особенно критично для Shop DB, которую используют одновременно Shop API и CRM API.
   * **Ярлыки:** `db_instance`, `application_name` (shop-api, crm-api, mes-api).

10. **`database_slow_queries_total`** (Counter)
    * **Зачем нужна:** Количество запросов, выполняющихся дольше порогового значения (например, > 1 секунды). Поможет выявить проблемные запросы, которые тормозят дашборд MES.
    * **Ярлыки:** `db_instance`, `query_type` (SELECT, INSERT, UPDATE, DELETE).

11. **`disk_io_utilization_percent`** (Gauge)
    * **Зачем нужна:** Показывает насыщенность дисковой подсистемы. Поскольку БД работают и на чтение, и на запись, высокий IO Wait является частой причиной медленных выборок данных для дашбордов.
    * **Ярлыки:** `instance`, `device`.

### Метрики хранилища 3D-файлов (3d files storage)

12. **`s3_request_duration_seconds`** (Histogram)
    * **Зачем нужна:** Время загрузки и выгрузки 3D-файлов. Медленное хранилище может быть узким местом при расчете стоимости.
    * **Ярлыки:** `operation` (upload, download), `file_size_bucket`.

13. **`s3_storage_usage_bytes`** (Gauge)
    * **Зачем нужна:** Объем используемого хранилища. Поможет прогнозировать рост затрат и планировать масштабирование.
    * **Ярлыки:** `storage_class` (standard, infrequent_access).

### Метрики фронтендов (Подход «Четыре золотых сигнала»)

14. **`frontend_page_load_duration_seconds`** (Histogram)
    * **Зачем нужна:** Время загрузки страниц Internet Shop, CRM и MES. Критично для операторов MES, которые жалуются на медленный дашборд.
    * **Ярлыки:** `application` (internet-shop, crm, mes), `page` (dashboard, order-details, catalog).

15. **`frontend_errors_total`** (Counter)
    * **Зачем нужна:** Количество JavaScript ошибок и неудачных запросов к API с фронтенда. Поможет выявить проблемы на клиентской стороне.
    * **Ярлыки:** `application`, `error_type` (js_error, api_error).

### Дополнительная кастомная метрика (Специфичная для бизнеса)

16. **`orders_stuck_in_status_duration_seconds`** (Gauge/Histogram)
    * **Зачем нужна:** Специальная метрика для контроля SLA. Она отслеживает время, которое заказ проводит в "опасных" статусах (например, `SUBMITTED` без перехода в `PRICE_CALCULATED` более 5 минут, или `MANUFACTURING_APPROVED` без перехода в `MANUFACTURING_STARTED` более 24 часов).
    * **Ярлыки:** `current_status`, `order_source` (b2c, b2b).
    * *Обоснование:* Эта метрика напрямую ложится на дашборд для продакт-менеджера и тимлида, позволяя мгновенно видеть "зависшие" заказы, о которых жалуются клиенты, еще до того, как клиент позвонит менеджеру.


## 4. План действий (Драфт технического задания)

Для реализации системы мониторинга предлагается выполнить следующие высокоуровневые задачи:

1. **Развертывание инфраструктуры мониторинга:** 
   - Создать инстанс Time-Series базы данных (рекомендуется Yandex Managed Service for Prometheus или развертывание Prometheus + VictoriaMetrics на выделенном EC2).
   - Развернуть инстанс Grafana для визуализации и настройки алертинга.
   - Настроить Yandex Cloud Monitoring для сбора метрик инфраструктуры (EC2, Managed PostgreSQL, RabbitMQ).

2. **Инструментация приложений (Instrumentation):**
   - Подключить библиотеки экспортеров метрик: `Micrometer/Prometheus` для Java-сервисов (Shop API, CRM API), `prometheus-net` для C#-сервиса (MES API).
   - Настроить и развернуть `RabbitMQ Exporter` для снятия метрик с Messages Queue.
   - Добавить клиентские метрики в фронтенды (Internet Shop, CRM, MES) с использованием Prometheus Client для JavaScript.
   - Настроить сбор метрик инфраструктуры с EC2 и Yandex Managed Databases через `Node Exporter` и встроенные интеграции Yandex Cloud Monitoring.
   - Настроить мониторинг 3d files storage (S3) через AWS CloudWatch Exporter или аналог для Yandex Object Storage.

3. **Создание дашбордов:**
   - Разработать дашборд "SRE/DevOps" (здоровье инфраструктуры, очереди, ошибки 5xx, нагрузка на БД).
   - Разработать дашборд "Бизнес-процессы" (воронка прохождения заказа, застрявшие заказы, время расчета MES).
   - Разработать дашборд "Производительность MES" (время отклика MES DB, загрузка дашборда операторов, время расчета 3D-моделей).
   - Разработать дашборд "Фронтенды" (время загрузки страниц, ошибки на клиенте).

4. **Настройка алертинга и маршрутизации:**
   - Настроить правила (Alerting Rules) в Prometheus для критических порогов.
   - Интегрировать Alertmanager с корпоративным мессенджером (Telegram/Slack) и системой тикетов (Jira) для автоматического создания задач при критических сбоях.
   - Настроить алерты для бизнес-метрик (застрявшие заказы, потерянные сообщения в очереди).

5. **Документирование и онбординг:**
   - Написать краткую инструкцию для команды (как читать дашборды, как реагировать на алерты).
   - Провести демонстрацию для продакт-менеджера и тимлида.
   - Настроить runbook для типичных инцидентов (например, "Что делать, если RabbitMQ queue depth > 1000").


## 5. Показатели насыщенности и пороговые значения (Дополнительное задание)

Насыщенность (Saturation) означает, что ресурс полностью загружен, и новые запросы вынуждены ждать в очереди или отбрасываются. Для нашей системы критически важны следующие показатели:

| Показатель насыщенности | Пороговое значение | Почему выбрано это значение | Действия при превышении |
| :--- | :--- | :--- | :--- |
| **Глубина очереди RabbitMQ** (`rabbitmq_queue_depth`) | > 500 сообщений или рост > 50 сообщ./мин в течение 10 минут | Указывает на то, что потребители (MES API/CRM API) не справляются с потоком или упали. Заказы перестают двигаться. | 1. Мгновенный алерт в канал DevOps/Backend.<br>2. Автоматическое создание тикета в Jira с высоким приоритетом.<br>3. Проверка логов потребителей на наличие дедлоков или ошибок. |
| **Использование пула соединений MES DB** (`database_active_connections`) | > 80% от `max_connections` | При 100% новые запросы (включая загрузку дашборда MES) будут получать ошибку "Too many connections" или зависать в ожидании. | 1. Алерт команде бэкенда.<br>2. Экстренная проверка на наличие "утечек" соединений или медленных запросов, блокирующих пул.<br>3. Если проблема персистентна: ручное или автоматическое масштабирование инстанса MES DB (Vertical Scaling). |
| **Использование пула соединений Shop DB** (`database_active_connections`) | > 80% от `max_connections` | Shop DB используется одновременно Shop API и CRM API. При высокой нагрузке оба приложения могут конкурировать за соединения. | 1. Алерт команде бэкенда.<br>2. Анализ распределения соединений между Shop API и CRM API.<br>3. Рассмотрение выделения отдельной БД для CRM API. |
| **Загрузка CPU инстансов приложений** (EC2) | > 85% в течение 5 минут | При такой загрузке приложение начинает троттлить запросы, увеличивается время отклика, растут таймауты. | 1. Алерт DevOps-инженеру.<br>2. Триггер для Auto Scaling Group (если настроен) для добавления второго инстанса за балансировщиком.<br>3. Если масштабирование невозможно: временное включение Circuit Breaker для B2B API, чтобы спасти B2C-сегмент. |
| **Время расчета стоимости заказа** (`3d_calculation_duration_seconds`) | P95 > 10 минут (при норме 2-3 мин) | Означает, что вычислительный ресурс MES API или MES DB перегружен сложными запросами. Это прямая причина жалоб клиентов. | 1. Алерт тимлиду и C#-разработчику.<br>2. Автоматическая отправка уведомления менеджеру по продажам о возможной задержке конкретных заказов.<br>3. Анализ метрики `model_complexity_bucket` для выявления аномально тяжелых моделей. |
| **Время загрузки дашборда MES** (`frontend_page_load_duration_seconds`) | P95 > 3 секунд | Операторы жалуются на медленный интерфейс. Это напрямую влияет на их эффективность и вознаграждение. | 1. Алерт команде MES.<br>2. Проверка метрик MES DB (медленные запросы, нагрузка CPU).<br>3. Проверка метрик MES API (время отклика). |
| **Количество медленных запросов MES DB** (`database_slow_queries_total`) | > 20 запросов/мин (> 1 сек) | Указывает на проблемы с индексами или блокировками в базе данных производства. | 1.
