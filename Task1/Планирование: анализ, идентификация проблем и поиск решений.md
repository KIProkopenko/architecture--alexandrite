# Планирование: анализ, идентификация проблем и поиск решений

## 1. Анализ и идентификация проблемных мест

На основе C4-диаграммы архитектуры системы «Александрит» выявлены следующие существующие и потенциальные проблемы:

### Критические проблемы (влияют на бизнес прямо сейчас)

**1. Единая точка отказа в интеграции CRM ↔ MES (RabbitMQ)**
- **Проблема**: Все сообщения между CRM API и MES API проходят через единственную очередь RabbitMQ. При сбое брокера сообщений или переполнении очереди заказы теряются или зависают.
- **Симптомы**: Жалобы клиентов и B2B-партнеров на потерянные заказы.
- **Риск**: Полная остановка обмена данными между CRM и производством.

**2. Деградация производительности MES API и MES DB**
- **Проблема**: MES API обслуживает и расчет стоимости 3D-моделей (до 30 минут на сложные модели), и интерфейс операторов (дашборд со списком заказов). MES DB работает в режиме single instance (один инстанс на запись и чтение).
- **Симптомы**: Операторы жалуются на медленную загрузку дашборда, несмотря на пагинацию и фильтры.
- **Причина**: Тяжелые запросы к единственному инстансу БД, отсутствие индексов, блокировки таблиц при длительных транзакциях расчета стоимости.

**3. Общая Shop DB для Shop API и CRM API**
- **Проблема**: Shop DB (PostgreSQL) используется одновременно Shop API (онлайн-магазин) и CRM API (управление заказами). Оба приложения читают и пишут в одну базу.
- **Риск**: Конфликты блокировок, деградация производительности при росте нагрузки, особенно в часы пик.

**4. Отсутствие горизонтального масштабирования**
- **Проблема**: Каждый компонент системы (Shop API, CRM API, MES API, Shop DB, MES DB) работает на одном инстансе. Нет балансировщиков нагрузки, нет реплик БД.
- **Риск**: При росте нагрузки (100+ заказов в месяц) система достигнет предела производительности и начнет деградировать.

### Потенциальные проблемы (проявятся при росте)

**5. Синхронный расчет стоимости в MES API**
- **Проблема**: Расчет стоимости 3D-модели выполняется синхронно в рамках запроса к MES API. Это блокирует поток обработки и может привести к таймаутам.
- **Риск**: При высокой нагрузке MES API перестанет отвечать на запросы от API user и MES (фронтенд операторов).

**6. Отсутствие мониторинга и наблюдаемости**
- **Проблема**: Нет системы мониторинга, логирования и трейсинга. Проблемы обнаруживаются только по жалобам клиентов.
- **Риск**: Длительное время обнаружения и устранения инцидентов (MTTD/MTTR), потеря заказов без возможности расследования, невозможность оценить эффективность оптимизаций.

**7. Ручные процессы деплоя и тестирования**
- **Проблема**: Деплой в release и prod выполняется вручную. E2E-тестирование проводится вручную QA-инженером.
- **Риск**: Задержки релизов на недели/месяцы, человеческие ошибки при деплое, невозможность быстро доставить критические исправления.

 

## 2. Список инициатив для устранения проблем

### Инициатива 1: Внедрение мониторинга, логирования и трейсинга
- Развернуть систему мониторинга (Prometheus + Grafana) для сбора метрик RED/USE.
- Настроить централизованное логирование (ELK/EFK или Loki) с маскировкой PII.
- Внедрить распределенный трейсинг (OpenTelemetry + Jaeger) для отслеживания пути заказа.
- Настроить алертинг на критичные метрики (глубина очереди, время отклика, ошибки).
- **Цель**: Получить объективные данные для диагностики проблем и оценки эффективности всех последующих изменений.

### Инициатива 2: Стабилизация обмена сообщениями (RabbitMQ)
- Внедрить механизмы гарантированной доставки: обязательные ACK/NACK, retry с экспоненциальной задержкой.
- Настроить Dead Letter Queue (DLQ) для обработки неудачных сообщений.
- Добавить идемпотентность обработчиков (защита от дубликатов).
- Настроить мониторинг глубины очереди и алертинг при росте.

### Инициатива 3: Оптимизация производительности MES API и MES DB
- Провести анализ медленных запросов (slow query log) в MES DB.
- Добавить индексы по часто используемым полям (status, created_at, operator_id).
- Выделить реплику MES DB только для чтения (Read Replica) для дашборда операторов.
- Разделить нагрузку: вынести расчет стоимости в отдельный фоновый процесс/сервис.

### Инициатива 4: Повышение отказоустойчивости инфраструктуры
- Перевести Shop DB и MES DB в режим High Availability (Master-Replica с автоматическим failover).
- Добавить второй инстанс для критичных API (Shop API, CRM API, MES API) с балансировщиком нагрузки.
- Настроить Auto Scaling для обработки пиковых нагрузок.

### Инициатива 5: Асинхронность расчета стоимости
- Вынести расчет стоимости 3D-моделей в отдельный фоновый воркер.
- MES API принимает запрос, сохраняет задачу в очередь, возвращает клиенту статус "в обработке".
- Отдельный сервис (или воркер) обрабатывает задачи и обновляет статус заказа через RabbitMQ.

### Инициатива 6: Автоматизация CI/CD и тестирования
- Передать прототипы автоматизации QA-инженеру в работу.
- Настроить автоматический запуск E2E-тестов в CI/CD пайплайне.
- Перевести деплой в release/prod на полуавтоматический режим (одна кнопка после прохождения тестов).
- Настроить автоматические rollback при обнаружении критичных ошибок.

### Инициатива 7: Усиление команды
- Нанять второго бэкенд-разработчика (C# или Java с готовностью перейти на C#) для работы над MES API.
- Расширить команду DevOps для поддержки растущей инфраструктуры.

 

## 3. Приоритизация и обоснование

Инициативы расставлены в порядке убывания приоритета:

1. **Внедрение мониторинга, логирования и трейсинга** — *Почему*: Это фундамент. Без наблюдаемости мы не можем эффективно диагностировать текущие проблемы, оценивать риски и измерять эффект от любых оптимизаций. Любые изменения "вслепую" могут ухудшить ситуацию. Мониторинг даст нам baseline и уверенность.

2. **Стабилизация обмена сообщениями (RabbitMQ)** — *Почему*: Это прямая причина потери заказов и жалоб B2B-партнеров. Без надежной доставки заказов бизнес теряет деньги прямо сейчас. Имея мониторинг (п.1), мы сможем точно настроить алерты и убедиться, что проблема решена.

3. **Оптимизация производительности MES API и MES DB** — *Почему*: Операторы не могут эффективно работать из-за медленного дашборда. Это "быстрая победа" (Quick Win), которая сразу улучшит операционную эффективность. Мониторинг поможет выявить конкретные медленные запросы.

4. **Повышение отказоустойчивости инфраструктуры** — *Почему*: Текущая архитектура не масштабируется. При росте нагрузки система достигнет предела и начнет деградировать.

5. **Асинхронность расчета стоимости** — *Почему*: Синхронный расчет блокирует MES API и создает узкое место. Требует рефакторинга, но критичен для долгосрочного масштабирования.

6. **Автоматизация CI/CD и тестирования** — *Почему*: Необходима для ускорения доставки исправлений и новых функций. Без автоматизации команда не сможет быстро реагировать на проблемы.

7. **Усиление команды** — *Почему*: Найм занимает время (1-3 месяца), но необходим для долгосрочного развития. Начать процесс нужно сейчас.

 

## 4. Целевая архитектура через полгода

Через полгода архитектура «Александрита» должна трансформироваться в отказоустойчивую, масштабируемую систему:

**Инфраструктура:**
- Все критичные сервисы (Shop API, CRM API, MES API) работают как минимум на двух инстансах за балансировщиком нагрузки.
- Базы данных (Shop DB, MES DB) работают в конфигурации Master-Replica с автоматическим failover. Выделены Read-реплики для аналитических запросов (дашборд MES).
- RabbitMQ работает в кластерном режиме с зеркалированием очередей.

**Интеграции:**
- Взаимодействие через RabbitMQ стало надежным: внедрены DLQ, retry, идемпотентность.
- Расчет стоимости 3D-моделей вынесен в отдельный асинхронный процесс.
- Настроен централизованный мониторинг (Prometheus/Grafana), логирование (ELK/Loki) и трейсинг (Jaeger).

**Процессы:**
- CI/CD пайплайн автоматизирован: деплой в prod происходит после автоматического прохождения тестов.
- Время доставки исправлений сокращено с месяцев до дней/часов.

**Команда:**
- Команда бэкенда усилена вторым разработчиком.
- QA-инженер успешно автоматизировал основные E2E-сценарии.

 

## 5. Топ-3 инициативы на ближайшие полгода

Если бы я мог выполнить только три пункта, я бы выбрал:

### 1. Внедрение мониторинга, логирования и трейсинга
**Обоснование**: Это база для любой инженерной работы. Сейчас мы действуем вслепую. Мониторинг позволит нам:
- Точно диагностировать причины потери заказов (RabbitMQ vs DB vs API).
- Измерить текущую производительность MES (baseline).
- Безопасно проводить оптимизации, видя их эффект в реальном времени.
- Снизить MTTD (время обнаружения проблем) с часов до минут.

### 2. Стабилизация обмена сообщениями (RabbitMQ + DLQ + Идемпотентность)
**Обоснование**: Это остановит прямую потерю выручки. B2B-партнеры уходят из-за ненадежности. Внедрение DLQ и retry решит проблему "черной дыры", куда пропадают заказы. Имея мониторинг (п.1), мы сможем настроить точные алерты на глубину очереди и убедиться в надежности решения.

### 3. Оптимизация MES DB и внедрение Read Replica для дашборда
**Обоснование**: Это решит главную операционную боль операторов. Создание реплики в Managed Service Yandex Cloud делается быстро. Добавление индексов даст мгновенный прирост скорости. Операторы смогут видеть и брать новые заказы без задержек, что увеличит пропускную способность производства. Мониторинг покажет, какие именно запросы тормозят систему.
