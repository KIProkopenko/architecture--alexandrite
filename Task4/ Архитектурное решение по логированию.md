# Архитектурное решение по логированию

## 1. Анализ системы и планирование логирования

На основе C4-диаграммы выявлены следующие системы, требующие обязательного сбора логов:

### Системы для сбора логов (отмечены на схеме):
1. **Shop API** (SpringBoot) — бэкенд интернет-магазина
2. **CRM API** (SpringBoot) — бэкенд CRM-системы
3. **MES API** (C#) — бэкенд производственной системы
4. **Messages Queue** (RabbitMQ) — брокер сообщений
5. **Shop DB** (PostgreSQL) — база данных магазина
6. **MES DB** (PostgreSQL) — база данных производственной системы

### Список логов уровня INFO:

#### Shop API:
- **Создание заказа**: время, `OrderID`, `UserID`, `OrderSource` (B2C/B2B), общая сумма заказа
- **Загрузка 3D-файла**: время, `OrderID`, `UserID`, размер файла, формат файла
- **Изменение статуса заказа**: время, `OrderID`, `OldStatus`, `NewStatus`, инициатор изменения
- **Авторизация пользователя**: время, `UserID`, IP-адрес, результат (успех/неудача)
- **Расчет стоимости**: время, `OrderID`, `ModelComplexity` (количество полигонов), время расчета

#### CRM API:
- **Получение заказа из очереди**: время, `OrderID`, `TraceID`, источник сообщения
- **Подтверждение заказа менеджером**: время, `OrderID`, `SellerID`, комментарий
- **Экспорт заказа в производство**: время, `OrderID`, `SellerID`, статус `MANUFACTURING_APPROVED`
- **Закрытие заказа**: время, `OrderID`, `SellerID`, финальный статус, причина закрытия

#### MES API:
- **Получение заказа на расчет**: время, `OrderID`, `TraceID`, путь к 3D-файлу
- **Начало расчета стоимости**: время, `OrderID`, `OperatorID` (если назначен), сложность модели
- **Завершение расчета**: время, `OrderID`, рассчитанная стоимость, время выполнения (мс)
- **Назначение заказа оператору**: время, `OrderID`, `OperatorID`, статус `MANUFACTURING_STARTED`
- **Изменение статуса производства**: время, `OrderID`, `OperatorID`, `OldStatus`, `NewStatus`
- **Завершение производства**: время, `OrderID`, `OperatorID`, фактическое время выполнения

#### RabbitMQ:
- **Публикация сообщения**: время, `Exchange`, `RoutingKey`, `MessageID`, `OrderID`, размер сообщения
- **Потребление сообщения**: время, `Queue`, `MessageID`, `OrderID`, `ConsumerTag`, время обработки
- **Подтверждение обработки (ACK)**: время, `MessageID`, `OrderID`, результат
- **Отказ в обработке (NACK/Reject)**: время, `MessageID`, `OrderID`, причина, действие (retry/DLQ)
- **Попадание в DLQ**: время, `MessageID`, `OrderID`, причина, количество попыток

#### PostgreSQL (Shop DB, MES DB):
- **Долгие запросы** (> 1 секунда): время, имя таблицы, тип операции (SELECT/INSERT/UPDATE), время выполнения, количество затронутых строк
- **Ошибки запросов**: время, текст ошибки, SQL-запрос (без чувствительных данных), стек вызовов
- **Блокировки (Deadlocks)**: время, затронутые таблицы, транзакции-участники
- **Подключение к БД**: время, имя приложения, пользователь, IP-адрес

### Другие уровни логирования:

**DEBUG**:
- Детальная информация о каждом шаге обработки запроса
- Входящие и исходящие HTTP-заголовки
- SQL-запросы с параметрами (только в dev/test окружениях)
- Состояние очередей в деталях
- *Использовать*: при отладке конкретных инцидентов, временно включать в production для расследования

**WARN**:
- Повторные попытки обработки сообщения (retry)
- Приближение к лимитам (пул соединений БД > 80%, место на диске > 85%)
- Нестандартные ситуации, которые не являются ошибками, но требуют внимания
- Устаревшие API-версии в запросах
- *Использовать*: всегда, для проактивного обнаружения проблем

**ERROR**:
- Необработанные исключения
- Ошибки валидации входных данных
- Недоступность внешних сервисов (БД, RabbitMQ, S3)
- Ошибки бизнес-логики (невозможно рассчитать стоимость, заказ не найден)
- *Использовать*: всегда, для реактивного реагирования на сбои

**FATAL/CRITICAL**:
- Падение приложения
- Невозможность подключения к критичным зависимостям (БД, брокер сообщений)
- Потеря данных
- *Использовать*: всегда, требует немедленного вмешательства


## 2. Мотивация

Внедрение централизованной системы логирования критически необходимо для компании «Александрит» по следующим причинам:

1. **Сокращение времени на диагностику**: Сейчас разработчики и поддержка тратят часы на сбор информации "со слов клиента" и ручной поиск в разрозненных логах. Централизованное логирование позволит за минуты найти полную историю прохождения заказа по всем системам.

2. **Снижение нагрузки на поддержку**: Специалисты поддержки смогут самостоятельно анализировать большинство типовых проблем, не привлекая разработчиков. Это освободит до 40% времени команды разработки.

3. **Проактивное обнаружение проблем**: Алертинг на основе логов позволит узнавать о проблемах до того, как о них сообщат клиенты.

4. **Соответствие SLA**: Точное логирование времени каждого этапа обработки заказа позволит контролировать соблюдение соглашений об уровне сервиса.

5. **Аудит и расследование инцидентов**: Полная история изменений заказов необходима для расследования спорных ситуаций с клиентами и партнерами.

### Метрики, на которые повлияет внедрение логирования:

**Технические метрики:**
1. **MTTR (Mean Time To Resolution)** — среднее время устранения инцидентов. Целевое снижение с текущих 4-6 часов до 30-60 минут.
2. **MTTD (Mean Time To Detection)** — среднее время обнаружения проблемы. Целевое снижение с нескольких часов (когда позвонит клиент) до 5-10 минут (алерт).
3. **Процент ошибок, воспроизведенных в dev-среде** — увеличится с текущих ~30% до 80%+ благодаря детальной информации из логов.
4. **Количество эскалаций на разработчиков** — снизится на 50-60% за счет возможности самостоятельного анализа поддержки.

**Бизнес-метрики:**
1. **Количество жалоб на "потерянные" заказы** — снизится на 70-80% благодаря возможности быстро найти заказ в любой системе.
2. **NPS (Net Promoter Score)** — увеличится за счет сокращения времени реакции на проблемы и повышения прозрачности статуса заказа.
3. **Время выполнения заказа (Order Fulfillment Time)** — сократится на 15-20% за счет быстрого выявления и устранения узких мест в процессах.


## 3. Приоритизация: с чего начать

Учитывая ограниченность ресурсов команды и критичность текущих проблем, логирование и трейсинг следует внедрять в следующем порядке:

### Первый приоритет (недели 1-4):
1. **MES API (C#)** — источник самых серьезных проблем с производительностью и "зависающими" заказами. Здесь происходит расчет стоимости (до 30 минут), и именно здесь чаще всего теряются заказы.
2. **RabbitMQ** — критичный компонент интеграции. Потеря сообщений в очереди — основная причина жалоб клиентов.
3. **Shop API (SpringBoot)** — точка входа для B2C-клиентов и B2B-API. Необходимо логировать все входящие запросы для быстрого расследования жалоб.

**Почему именно эти системы:**
- Они находятся в эпицентре текущих проблем (потеря заказов, долгие расчеты)
- Дадут максимальный эффект в краткосрочной перспективе
- Позволят отслеживать полный путь заказа от создания до расчета стоимости

### Второй приоритет (недели 5-8):
4. **CRM API (SpringBoot)** — для контроля работы менеджеров и подтверждения заказов
5. **PostgreSQL (Shop DB и MES DB)** — для выявления проблем с производительностью запросов
6. **Трейсинг (OpenTelemetry)** — интеграция с системой трейсинга из Задания 3

### Третий приоритет (недели 9-12):
7. **Фронтенды (Internet Shop, CRM, MES)** — логирование действий пользователей на клиентской стороне
8. **3D files storage (S3)** — логирование операций с файлами


## 4. Предлагаемое решение

### Архитектура системы логирования

Для реализации централизованного сбора, хранения и анализа логов предлагается использовать стек **ELK (Elasticsearch, Logstash, Kibana)** или **EFK (Elasticsearch, Fluentd/Fluent Bit, Kibana)** с дополнительными компонентами.

#### Компоненты:

1. **Filebeat/Fluent Bit** (агенты сбора логов):
   - Устанавливаются на каждый сервер с приложениями (EC2 инстансы)
   - Читают лог-файлы приложений и отправляют их в Logstash/Kafka
   - Минимальное потребление ресурсов (< 5% CPU, < 100MB RAM)
   - Поддержка буферизации на случай недоступности центрального сервера

2. **Kafka** (буфер сообщений):
   - Принимает логи от всех агентов
   - Сглаживает пиковые нагрузки
   - Гарантирует доставку логов даже при временной недоступности Elasticsearch
   - Хранение логов 24-48 часов для повторной обработки

3. **Logstash** (обработка и обогащение):
   - Парсит неструктурированные логи
   - Обогащает логи мета-данными (имя сервера, окружение, версия приложения)
   - Фильтрует чувствительные данные (маскировка email, телефонов, номеров карт)
   - Нормализует форматы логов из разных источников

4. **Elasticsearch** (хранилище и поиск):
   - Полнотекстовый поиск по логам
   - Агрегации для аналитики
   - Индексы с разделением по времени (daily indices)
   - Репликация для отказоустойчивости

5. **Kibana** (визуализация и анализ):
   - Дашборды для мониторинга
   - Поиск и фильтрация логов
   - Alerting (встроенный или через ElastAlert)

6. **Prometheus + Alertmanager** (алертинг):
   - Сбор метрик из логов (количество ошибок, время обработки)
   - Правила алертинга
   - Маршрутизация уведомлений (Telegram, Slack, Email, Jira)

#### Схема архитектуры:

```
[Приложения] → [Filebeat] → [Kafka] → [Logstash] → [Elasticsearch] → [Kibana]
                     ↓                              ↓
                [Prometheus] ← [Metrics Exporter]  → [Alertmanager] → [Telegram/Slack/Jira]
```

**На схеме C4 необходимо добавить:**
- **Filebeat** (агент) — на каждом сервере с приложениями (Shop API, CRM API, MES API, RabbitMQ, PostgreSQL)
- **Kafka Cluster** — отдельный контейнер/сервис
- **Logstash** — отдельный контейнер/сервис
- **Elasticsearch Cluster** — отдельный контейнер/сервис (минимум 3 узла)
- **Kibana** — отдельный контейнер/сервис
- **Prometheus** — отдельный контейнер/сервис
- **Alertmanager** — отдельный контейнер/сервис

Стрелки:
- От Filebeat на каждом приложении → Kafka
- От Kafka → Logstash
- От Logstash → Elasticsearch
- От Elasticsearch → Kibana
- От Elasticsearch → Prometheus (через exporter)
- От Prometheus → Alertmanager
- От Alertmanager → Telegram/Slack/Jira

### Политика безопасности

#### Работа с чувствительными данными:

1. **Маскировка на уровне приложения**:
   - Запрет логирования паролей, токенов, секретных ключей
   - Маскировка email (user***@example.com)
   - Маскировка телефонов (+7 *** *** ** 45)
   - Хэширование UserID (SHA-256 с солью) для аналитики

2. **Маскировка на уровне Logstash**:
   - Grok-фильтры для выявления и замены PII (Personally Identifiable Information)
   - Регулярные выражения для поиска номеров карт, паспортов, ИНН
   - Удаление или хэширование полей с персональными данными

3. **Контроль доступа**:
   - **Role-Based Access Control (RBAC)** в Kibana:
     - **Support** — доступ только к логам уровня ERROR/WARN, без чувствительных данных
     - **Developer** — доступ ко всем логам своих сервисов, DEBUG-логи в dev/test
     - **DevOps** — полный доступ ко всем логам и конфигурации
     - **Manager** — доступ только к агрегированным дашбордам и метрикам
   - Интеграция с корпоративным SSO (Keycloak/Yandex ID)
   - Аудит действий в Kibana (кто, когда, что искал)

4. **Шифрование**:
   - TLS для передачи логов между компонентами
   - Шифрование данных на диске (Elasticsearch encryption at rest)
   - Закрытые сети (VPC) для инфраструктуры логирования

#### Политика хранения:

1. **Разделение по индексам**:
   - `logs-app-{yyyy.MM.dd}` — логи приложений (Shop API, CRM API, MES API)
   - `logs-rabbitmq-{yyyy.MM.dd}` — логи брокера сообщений
   - `logs-db-{yyyy.MM.dd}` — логи баз данных
   - `logs-audit-{yyyy.MM.dd}` — аудит-логи (изменения заказов, доступы)

2. **Сроки хранения**:
   - **DEBUG** — 3 дня (только для расследования инцидентов)
   - **INFO** — 30 дней (оперативный анализ)
   - **WARN/ERROR/FATAL** — 90 дней (расследование инцидентов)
   - **AUDIT** (изменения заказов, доступы) — 1 год (требования compliance)
   - **Архив** — логи старше 90 дней сжимаются и переносятся в холодное хранилище (S3 Glacier)

3. **Размер и масштабирование**:
   - Ожидаемый объем: ~50-100 GB/день (при текущей нагрузке)
   - Хранение 30 дней: ~1.5-3 TB
   - Elasticsearch cluster: минимум 3 узла (16 GB RAM, 8 CPU, 2 TB SSD каждый)
   - ILM (Index Lifecycle Management) для автоматического управления жизненным циклом индексов

### Превращение в систему анализа логов

#### 1. Алертинг:

Настроить алерты в Prometheus/Alertmanager или ElastAlert:

**Критичные алерты (немедленное уведомление в Telegram/Slack + звонок):**
- `ERROR rate > 10/мин` для любого сервиса
- `FATAL log` — любое появление
- `RabbitMQ: messages in DLQ > 100`
- `Database: deadlock detected`
- `Service unavailable` (недоступность сервиса > 2 минут)

**Предупреждающие алерты (уведомление в канал + создание тикета в Jira):**
- `WARN rate > 50/мин`
- `Response time p95 > 5 секунд`
- `Database: slow queries > 20/мин`
- `Disk space < 15%`
- `RabbitMQ: queue depth > 1000`

**Информационные алерты (ежедневный дайджест):**
- Количество созданных заказов за день
- Среднее время расчета стоимости
- Топ-5 самых частых ошибок

#### 2. Поиск аномалий:

**Статистические методы:**
- **Базовая линия (baseline)**: собрать статистику за 2 недели нормальной работы
- **Отклонения от базовой линии**:
  - Количество заказов упало/выросло > 50% от среднего
  - Время обработки заказа выросло > 2x от среднего
  - Количество ошибок выросло > 3x от среднего

**Правила обнаружения аномалий:**

1. **DDoS-атака или всплеск нагрузки**:
   ```
   IF (rate(http_requests_total) > 10000/сек) AND 
      (rate(http_requests_total) > baseline * 10)
   THEN alert "Possible DDoS attack"
   ```

2. **Потеря сообщений в очереди**:
   ```
   IF (rabbitmq_messages_published - rabbitmq_messages_consumed) > 1000
      AND (rabbitmq_messages_unacked > 500)
   THEN alert "Message queue stuck"
   ```

3. **Аномальное время расчета**:
   ```
   IF (histogram_quantile(0.95, order_calculation_duration) > 600 сек)
      AND (histogram_quantile(0.95, order_calculation_duration) > baseline_p95 * 3)
   THEN alert "Calculation performance degradation"
   ```

4. **Необычная активность пользователя**:
   ```
   IF (rate(orders_by_user{user_id="X"}) > 100/час)
   THEN alert "Suspicious user activity"
   ```

**Инструменты для ML-анализа:**
- **Elasticsearch ML** (платный) — автоматическое обнаружение аномалий
- **Prometheus + Grafana** — правила на основе статистики
- **Custom scripts** — Python-скрипты с библиотеками (scikit-learn, pandas) для сложной аналитики

#### 3. Корреляция событий:

- Использовать **TraceID** для связывания логов из разных систем (интеграция с трейсингом)
- **CorrelationID** для каждого заказа — позволяет отследить полный путь заказа
- **Kibana Lens** — визуализация корреляций между метриками


## 5. Дополнительное задание: Критерии выбора технологии

### Критерии выбора:

#### 1. **Масштабируемость и производительность**

**Описание**: Способность системы обрабатывать растущий объем логов без деградации производительности.

**Требования**:
- Поддержка горизонтального масштабирования (добавление узлов)
- Индексация и поиск по терабайтам данных
- Время отклика при поиске < 3 секунд
- Пропускная способность > 10,000 событий/секунду

**Сравнение**:
- **Elasticsearch**: + Отличная горизонтальная масштабируемость, шардирование, репликация. - Требует значительных ресурсов RAM.
- **Graylog**: + Хорошая масштабируемость, но сложнее в настройке кластера. - Меньше гибкости в кастомизации.
- **Loki**: + Легковесный, низкое потребление ресурсов. - Ограниченная масштабируемость для очень больших объемов.

#### 2. **Стоимость владения (TCO)**

**Описание**: Общая стоимость владения, включая лицензии, инфраструктуру, поддержку и обучение.

**Требования**:
- Open-source решение (предпочтительно)
- Минимальные требования к инфраструктуре
- Низкие эксплуатационные расходы

**Сравнение**:
- **ELK Stack (Elasticsearch, Logstash, Kibana)**: + Бесплатный open-source (Apache 2.0). - Требует много ресурсов (RAM, CPU, диск). Высокая стоимость инфраструктуры.
- **EFK (Fluentd вместо Logstash)**: + Fluentd легче Logstash, меньше потребление RAM. - Схожая общая стоимость.
- **Loki + Promtail + Grafana**: + Значительно дешевле Elasticsearch (в 5-10 раз по ресурсам). + Интеграция с Prometheus/Grafana. - Меньше функционала полнотекстового поиска.
- **Graylog**: + Open-source версия бесплатна. - Enterprise-функции платные. Требует MongoDB + Elasticsearch.

#### 3. **Функциональность поиска и анализа**

**Описание**: Возможности полнотекстового поиска, агрегаций, визуализации и корреляции событий.

**Требования**:
- Полнотекстовый поиск с поддержкой сложных запросов
- Агрегации и статистика
- Гибкая визуализация (дашборды, графики)
- Корреляция событий по TraceID/CorrelationID

**Сравнение**:
- **Elasticsearch**: + Мощнейший полнотекстовый поиск (Lucene). + Богатые возможности агрегаций. + Kibana — отличная визуализация. + Встроенный ML для аномалий (платно). - Сложный DSL для запросов (требует обучения).
- **Loki**: + Простой запросный язык (LogQL). + Интеграция с Grafana. - Ограниченный полнотекстовый поиск (только по меткам и содержимому). - Меньше возможностей агрегации.
- **Graylog**: + Удобный интерфейс поиска. + Встроенные дашборды. - Меньше гибкости, чем Kibana.

#### 4. **Простота внедрения и эксплуатации**

**Описание**: Насколько легко развернуть, настроить и поддерживать систему.

**Требования**:
- Простая установка и конфигурация
- Наличие готовых интеграций с приложениями
- Активное сообщество и документация
- Автоматизация рутинных задач (ILM, бэкапы)

**Сравнение**:
- **ELK Stack**: + Огромное сообщество, тонны документации. + Готовые интеграции (Filebeat, Metricbeat, etc.). + Elastic Cloud — managed service. - Сложная настройка кластера. - Требует DevOps-экспертизы. - Частые breaking changes между версиями.
- **Loki**: + Простая архитектура (один бинарник). + Отличная интеграция с Grafana/Prometheus. - Меньше документации и примеров. - Меньше готовых интеграций.
- **Graylog**: + Проще в настройке, чем ELK. + Хорошая документация. - Меньшее сообщество.

#### 5. **Интеграция с существующей инфраструктурой**

**Описание**: Совместимость с текущим стеком технологий и облачной платформой.

**Текущий стек Alexandrite**:
- Yandex Cloud (Managed Kubernetes, Managed PostgreSQL)
- Java Spring Boot (Shop API, CRM API)
- C# (.NET Core, MES API)
- RabbitMQ
- Vue.js, React (фронтенды)

**Сравнение**:
- **ELK Stack**: + Официальная поддержка Java и .NET. + Filebeat работает на любых серверах. + Интеграция с RabbitMQ (плагин). + Yandex Cloud предлагает Managed Elasticsearch. - Требует отдельного кластера.
- **Loki**: + Отличная интеграция с Prometheus (уже используется для мониторинга). + Легко развернуть в Kubernetes. + Grafana уже используется для визуализации метрик. - Меньше нативной поддержки .NET.
- **Yandex Cloud Managed ELK**: + Полностью managed service. + Не нужно администрировать. + Интеграция с Yandex Cloud Monitoring. - Vendor lock-in. - Дороже self-hosted решения.

### Итоговая рекомендация:

**Для компании «Александрит» рекомендуется использовать Loki + Promtail + Grafana** по следующим причинам:

1. **Экономия ресурсов**: При текущей нагрузке и ограниченной команде DevOps, Loki потребует в 5-10 раз меньше ресурсов, чем Elasticsearch.
2. **Интеграция с мониторингом**: Если уже внедряется Prometheus для метрик (Задание 2) и трейсинга (Задание 3), Loki естественно дополнит этот стек.
3. **Простота**: Меньше компонентов для поддержки, проще архитектура.
4. **Достаточный функционал**: Для текущих задач (поиск по OrderID, TraceID, анализ ошибок) возможностей Loki достаточно.

**Альтернатива**: Если в будущем потребуется мощный полнотекстовый поиск и сложная аналитика, можно рассмотреть **Yandex Cloud Managed Elasticsearch** как платное, но полностью управляемое решение.
