# Архитектурное решение по кешированию

## 1. Мотивация

### Текущие проблемы системы

На основе анализа архитектуры и описания системы «Александрит» выявлены следующие критические проблемы производительности:

1. **Низкая скорость загрузки дашборда MES**: Операторы жалуются на медленную загрузку первой страницы системы, где отображается список заказов по статусам. Применение пагинации и фильтров не дало результата, что указывает на проблемы с базой данных.

2. **Долгое время расчета стоимости**: Расчет стоимости 3D-модели занимает в среднем 2-3 минуты, а для сложных моделей — до 30 минут. Это создает узкое место в обработке заказов.

3. **Потеря конкурентного преимущества**: Операторы не могут быстро брать новые заказы в работу, что влияет на их вознаграждение и общую скорость выполнения заказов.

### Цели внедрения кеширования

1. **Ускорение загрузки дашборда MES**: Сокращение времени отклика с текущих нескольких секунд/минут до < 1 секунды для часто запрашиваемых данных.

2. **Снижение нагрузки на базу данных MES**: Уменьшение количества повторяющихся запросов к PostgreSQL, особенно для данных, которые редко меняются (списки заказов в определенных статусах).

3. **Кеширование результатов расчетов**: Избежание повторных вычислений стоимости для идентичных или похожих 3D-моделей.

### Элементы системы для кеширования

1. **Список заказов для дашборда MES** (приоритет: высокий)
   - Закешированные данные: список заказов с фильтрацией по статусам
   - Частота обновления: при изменении статуса заказа
   - Ожидаемый эффект: ускорение загрузки дашборда в 10-50 раз

2. **Детали заказа** (приоритет: высокий)
   - Закешированные данные: полная информация о заказе
   - Частота обновления: при изменении любых данных заказа
   - Ожидаемый эффект: ускорение просмотра деталей заказа

3. **Результаты расчета стоимости 3D-моделей** (приоритет: средний)
   - Закешированные данные: стоимость для конкретной 3D-модели (хэш файла)
   - Частота обновления: при загрузке новой уникальной модели
   - Ожидаемый эффект: исключение повторных 30-минутных вычислений

4. **Справочные данные** (приоритет: низкий)
   - Закешированные данные: каталоги изделий, параметры материалов
   - Частота обновления: редко (раз в день/неделю)
   - Ожидаемый эффект: незначительное ускорение, но снижение нагрузки на БД

## 2. Предлагаемое решение

### Выбор типа кеширования: Серверное кеширование

**Решение**: Внедряем **серверное кеширование** с использованием распределенного кеша (Redis).

**Обоснование выбора серверного кеширования:**

| Критерий | Клиентское кеширование | Серверное кеширование | Выбор |
|----------|------------------------|----------------------|-------|
| **Общий доступ к данным** | Не подходит: каждый оператор имеет свой кеш | Подходит: все операторы видят одинаковые данные |   Серверное |
| **Актуальность данных** | Риск устаревания: разные клиенты могут иметь разные версии | Централизованное управление: один источник истины |   Серверное |
| **Безопасность** | Риск: чувствительные данные на клиенте | Контроль: данные остаются на сервере |   Серверное |
| **Нагрузка на сеть** | Высокая: передача полных данных каждому клиенту | Низкая: передача только измененных данных |   Серверное |
| **Сложность реализации** | Низкая: встроенные механизмы браузера | Средняя: требуется инфраструктура |    Оправдано |

**Почему клиентское кеширование не подходит:**
- Дашборд MES отображает общие данные (список всех заказов), которые должны быть одинаковыми для всех операторов
- При клиентском кешировании каждый оператор будет видеть свою версию данных, что приведет к конфликтам (два оператора могут взять один и тот же заказ)
- Чувствительные бизнес-данные (стоимость заказов, информация о клиентах) не должны храниться на клиентских устройствах

### Выбор паттерна кеширования: Cache-Aside (Lazy Loading)

**Решение**: Используем паттерн **Cache-Aside** для всех сценариев кеширования.

**Описание паттерна Cache-Aside:**

```
Чтение данных:
1. Приложение запрашивает данные из кеша
2. Если данные есть в кеше (cache hit) → возвращаем их
3. Если данных нет в кеше (cache miss):
   a. Читаем данные из базы данных
   b. Сохраняем данные в кеш
   c. Возвращаем данные

Запись данных:
1. Обновляем данные в базе данных
2. Инвалидируем (удаляем) данные в кеше
3. При следующем чтении данные будут загружены заново
```

**Сравнение паттернов:**

| Критерий | Cache-Aside | Write-Through | Refresh-Ahead | Выбор |
|----------|-------------|---------------|---------------|-------|
| **Простота реализации** | Высокая | Средняя | Низкая |   Cache-Aside |
| **Консистентность** | Хорошая (при правильной инвалидации) | Отличная | Отличная |    Достаточно |
| **Производительность записи** | Высокая (асинхронная инвалидация) | Низкая (синхронная запись) | Высокая |   Cache-Aside |
| **Нагрузка на БД** | Низкая (кешируем только читаемое) | Высокая (пишем всё) | Низкая |   Cache-Aside |
| **Подходит для MES** |   Да |    Нет (медленная запись) |    Частично |   Cache-Aside |

**Почему выбран Cache-Aside:**

1. **Оптимальное соотношение простоты и эффективности**: Паттерн легко реализовать в существующей архитектуре без значительных изменений кода.

2. **Гибкость**: Кешируются только те данные, которые действительно запрашиваются (не тратим память на ненужные данные).

3. **Отказоустойчивость**: При падении кеша система продолжает работать, просто обращаясь напрямую к базе данных.

4. **Подходит для нашего сценария**: 
   - Чтение происходит часто (операторы постоянно обновляют дашборд)
   - Запись происходит реже (изменение статуса заказа)
   - Данные могут быть незначительно устаревшими (несколько секунд) без критичных последствий

**Почему не подходят другие паттерны:**

**Write-Through:**
- Требует синхронной записи и в кеш, и в БД при каждом изменении
- Замедлит операции записи (критично для MES, где операторы постоянно меняют статусы)
- Избыточен для нашего случая: не все данные из БД нужны в кеше

**Refresh-Ahead:**
- Требует точного предсказания, какие данные понадобятся
- Сложно реализовать для динамического списка заказов
- Может загружать в кеш данные, которые никогда не будут запрошены
- Требует дополнительной инфраструктуры (фоновые задачи)

**Пояснение диаграммы:**

**Сценарий 1: Первое обращение (Cache Miss)**
- Шаги 1-9: Оператор открывает дашборд
- При первом обращении кеш пуст, данные загружаются из БД
- Данные сохраняются в кеш с TTL 300 секунд (5 минут)
- Общее время: 2-5 секунд (зависит от сложности запроса)

**Сценарий 2: Изменение статуса заказа**
- Шаги 10-18: Оператор берет заказ в работу
- Данные обновляются в БД
- Кеш инвалидируется (удаляется) для затронутых статусов
- Это гарантирует, что другие операторы увидят актуальное состояние

**Сценарий 3: Повторное обращение (Cache Hit)**
- Шаги 19-24: Оператор обновляет дашборд
- Данные загружаются из кеша (время отклика < 100ms)
- Ускорение в 20-50 раз по сравнению с обращением к БД

### Стратегия инвалидации кеша

**Выбранная стратегия: Комбинированная (программная + временная)**

Мы используем **двухуровневую стратегию инвалидации**:

1. **Программная инвалидация (Cache Invalidation on Write)**
   - При изменении данных (создание заказа, изменение статуса) немедленно удаляем соответствующие ключи из кеша
   - Примеры:
     ```
     Изменение статуса заказа с NEW на IN_PROGRESS:
     - DELETE cache:orders:NEW
     - DELETE cache:orders:IN_PROGRESS
     - DELETE cache:orders:ALL
     - DELETE cache:order:{orderId}
     ```

2. **Временная инвалидация (TTL - Time To Live)**
   - Устанавливаем время жизни для каждого ключа кеша
   - Даже если программная инвалидация не сработала, данные автоматически устареют
   - Разные TTL для разных типов данных:
     - Список заказов: 300 секунд (5 минут)
     - Детали заказа: 600 секунд (10 минут)
     - Результаты расчета стоимости: 86400 секунд (24 часа)
     - Справочные данные: 604800 секунд (7 дней)

**Обоснование выбора:**

| Стратегия | Плюсы | Минусы | Применимость |
|-----------|-------|--------|--------------|
| **Программная** |   Мгновенная актуальность<br>  Минимальная нагрузка |    Сложность реализации<br>   Риск пропустить инвалидацию |   Основной механизм |
| **Временная (TTL)** |   Простота<br>  Гарантия устаревания |    Данные могут быть неактуальны до истечения TTL |   Страховка |
| **По ключу (Key-based)** |   Точность |    Требует сложной структуры ключей |    Часть программной |
| **Полная очистка (Flush All)** |   Простота |    Потеря всего кеша<br>   Пиковая нагрузка на БД |    Не подходит |

**Почему комбинированная стратегия лучше других:**

1. **Программная инвалидация** обеспечивает актуальность данных:
   - Операторы видят изменения практически мгновенно (после следующего запроса)
   - Критично для сценария, когда несколько операторов работают с одними и теми же заказами

2. **TTL как защита от ошибок**:
   - Если разработчик забыл добавить инвалидацию в каком-то месте, данные все равно обновятся через 5 минут
   - Защита от "вечного" кеша при сбоях системы

3. **Гибкость**:
   - Разные TTL для разных данных (часто меняющиеся vs редко меняющиеся)
   - Возможность принудительной инвалидации через админ-панель

**Почему не подходят другие стратегии:**

**Только временная инвалидация (TTL):**
- В течение 5 минут операторы могут видеть устаревшие данные
- Два оператора могут взять один и тот же заказ (конфликт)
- Недопустимо для бизнес-критичных данных

**Только программная инвалидация:**
- Высокий риск человеческой ошибки (забыли инвалидировать)
- Сложно отследить все места изменения данных
- Требует идеальной дисциплины от разработчиков

**Полная очистка кеша (Flush All):**
- При высокой нагрузке приведет к "шторму" запросов к БД
- Все операторы одновременно начнут загружать данные из БД
- Может "положить" базу данных

### Реализация: Технические детали

**Выбор технологии: Redis**

**Обоснование:**
1. **Производительность**: До 100,000 операций в секунду
2. **Структуры данных**: Поддержка hash, list, set, sorted set (удобно для списков заказов)
3. **TTL**: Встроенная поддержка времени жизни ключей
4. **Persistence**: Возможность сохранения на диск (RDB/AOF)
5. **Cluster**: Горизонтальное масштабирование
6. **Интеграция**: Готовые клиенты для C# (.NET Core) и Java (Spring Boot)
7. **Managed Service**: Yandex Cloud предлагает Managed Redis (не нужно администрировать)

**Структура ключей кеша:**

```
# Списки заказов по статусам
cache:orders:{status}                    # Список ID заказов
cache:orders:{status}:page:{page}        # Пагинация
cache:orders:{status}:count              # Общее количество

# Детали заказа
cache:order:{orderId}                    # Полная информация о заказе
cache:order:{orderId}:status             # Только статус

# Результаты расчетов
cache:calculation:{fileHash}             # Стоимость для 3D-модели

# Справочные данные
cache:catalog:products                   # Каталог изделий
cache:materials:prices                   # Цены материалов

# Мета-информация
cache:version:orders                     # Версия кеша заказов (для массовой инвалидации)
```



### Ожидаемые результаты

**Метрики производительности:**

| Показатель | До кеширования | После кеширования | Улучшение |
|------------|----------------|-------------------|-----------|
| Время загрузки дашборда | 2-5 секунд | 100-300 мс | **10-50x** |
| Нагрузка на БД (запросов/сек) | 100-200 | 10-20 | **10x** |
| Количество медленных запросов (>1с) | 20-30% | < 1% | **20-30x** |
| Конфликты заказов (дубли) | 5-10 в день | 0-1 в день | **5-10x** |

**Бизнес-эффект:**
1. Операторы тратят меньше времени на ожидание загрузки интерфейса
2. Увеличивается количество обработанных заказов в день
3. Снижается количество жалоб от клиентов на медленную обработку
4. Уменьшается нагрузка на инфраструктуру (можно отложить масштабирование БД)

## 3. Дополнительное задание: Сравнение альтернативных решений

Рассмотрим два возможных подхода к реализации кеширования:

### Решение 1: Redis (распределенный кеш)

**Описание:**
- Выделенный сервер/кластер Redis
- Централизованное хранение кеша
- Доступ из всех инстансов приложений

**Плюсы:**
1.   **Масштабируемость**: Можно добавить реплики для чтения
2.   **Отказоустойчивость**: Redis Cluster или Sentinel обеспечивают HA
3.   **Общий кеш**: Все инстансы MES API видят одинаковые данные
4.   **Богатый функционал**: Pub/Sub, транзакции, Lua-скрипты
5.   **Persistence**: Данные не теряются при перезагрузке
6.   **Managed Service**: Yandex Cloud Managed Redis

**Минусы:**
1.    **Сложность инфраструктуры**: Нужно развернуть и поддерживать Redis
2.    **Сетевые задержки**: Дополнительный hop (приложение → Redis)
3.    **Стоимость**: Отдельный инстанс/кластер
4.    **Единая точка отказа**: Если Redis упадет, нагрузка ляжет на БД

### Решение 2: In-Memory кеш (IMemoryCache в .NET)

**Описание:**
- Кеш в памяти каждого экземпляра приложения
- Не требует внешней инфраструктуры
- Используется встроенный IMemoryCache

**Плюсы:**
1.   **Простота**: Не нужно разворачивать дополнительные сервисы
2.   **Производительность**: Нет сетевых задержек (в памяти процесса)
3.   **Стоимость**: Бесплатно (нет дополнительных ресурсов)
4.   **Отказоустойчивость**: Падение кеша не влияет на другие сервисы

**Минусы:**
1.    **Нет общего кеша**: Каждый инстанс хранит свои данные
2.    **Потеря данных**: При перезапуске приложения кеш очищается
3.    **Потребление памяти**: Кеш конкурирует с приложением за RAM
4.    **Сложность инвалидации**: Нужно инвалидировать на всех инстансах
5.    **Не масштабируется**: При добавлении инстансов эффективность падает

### Сравнительная таблица

| Критерий | Решение 1: Redis | Решение 2: In-Memory | Выбор |
|----------|------------------|----------------------|-------|
| **Производительность** | 10-50x ускорение | 50-100x ускорение |    In-Memory быстрее, но... |
| **Консистентность данных** |   Все операторы видят одинаковые данные |    Разные операторы могут видеть разные данные |   Redis |
| **Масштабируемость** |   Легко добавить инстансы |    Эффективность падает с ростом инстансов |   Redis |
| **Простота внедрения** |    Требует инфраструктуру |   Можно внедрить за 1 день |    In-Memory проще |
| **Надежность** |   Persistence, репликация |    Потеря данных при рестарте |   Redis |
| **Стоимость** | ~$50-200/мес (Managed Redis) | $0 |    In-Memory дешевле |
| **Подходит для MES** |   Да (общий кеш критичен) |    Нет (риск конфликтов) |   Redis |

### Заключение

**Выбранное решение: Redis (Распределенный кеш)**

**Обоснование:**

Несмотря на то, что In-Memory кеш проще в реализации и немного быстрее, для системы MES компании «Александрит» **критически важна консистентность данных** между всеми операторами. 

**Ключевые факторы выбора Redis:**

1. **Конкурентный доступ**: Несколько операторов одновременно работают с одними и теми же заказами. In-Memory кеш приведет к тому, что:
   - Оператор A увидит заказ как "NEW" и возьмет его в работу
   - Оператор B на другом инстансе тоже увидит заказ как "NEW" (его кеш не обновился)
   - Возникнет конфликт: два оператора работают с одним заказом

2. **Масштабируемость**: При росте нагрузки компания будет добавлять инстансы MES API. С In-Memory кешем эффективность будет падать (каждый инстанс хранит только 1/N данных), а с Redis — расти.

3. **Надежность**: Redis с persistence гарантирует, что при перезапуске приложения не произойдет "шторма" запросов к БД (все данные придется загружать заново).

4. **Управляемость**: Yandex Cloud Managed Redis снимает с команды нагрузку по администрированию (бэкапы, обновления, мониторинг).

**Когда можно рассмотреть In-Memory:**
- Если система работает на одном инстансе (нет горизонтального масштабирования)
- Если данные не критичны к консистентности (например, справочники)
- Как дополнительный уровень кеша (L1) перед Redis (L2)

**Рекомендация**: Начать с Redis как основного решения. Если в будущем возникнет необходимость еще больше ускорить доступ к часто читаемым данным, можно добавить двухуровневое кеширование:
- L1: In-Memory (самые "горячие" данные, TTL 30 секунд)
- L2: Redis (все остальные данные, TTL 5 минут)
